## Summary

A widget extension and the data it renders fail for different reasons, so the spike separates them. The widget component falls back to fixture values and draws even when the app has never sent it anything, which answers whether a sideloaded IPA carries an extension at all. A button on the spike screen then calls updateSnapshot with a random value and reloads, which answers whether the App Group data path works on this signing setup. Errors are surfaced on screen because there is no simulator and no console to read. The workflow also dumps every appex in the packaged IPA and every entitlements file, so an extension that never reached the bundle is distinguishable from one that failed to sign.

## Outcome

The spike is answered. A sideloaded IPA carries a widget extension that installs, appears in the gallery, and executes. App Groups are available to a free Apple account: iloader grants them, AltStore and SideStore do not.

The widget does not render. Two visual changes, a bright container background and a background on the library's red box, both failed to appear on device across several builds and two different signers. That points at the extension running stale code rather than at the group plumbing, and it is an install-layer problem rather than a code one.

Work stopped deliberately. The widget is stage 6 and nothing in stages 1 to 5 depends on it. Retry from a clean device before touching code: remove the widget, delete the app, reboot, reinstall.

Landed and kept:

- The App Group is resolved at runtime from the binary's own embedded profile, because every sideloader rewrites the identifier and nothing rewrites the Info.plist key expo-widgets reads.
- The granted groups are sorted before one is chosen, so the app and the extension cannot land on different groups when a signer grants several.
- The library's red box declares a container background, so widget errors are visible instead of being replaced by WidgetKit's placeholder.
- The red box names the widget, the resolved group, the configured group, and every granted group, which is the only view of the extension's own side.
- A signing facts screen and a provisioning profile dumper.

Two traps worth not repeating. `UserDefaults(suiteName:)` fails open, returning a process-local store when the entitlement is missing, so a round trip inside the app proves nothing. `containerURL` fails closed and is the honest probe. And "Please adopt containerBackground API" was a symptom three steps from its cause, which is why it survived a correct fix.
