# UI-022 execution plan

Date: 2026-09-15

Task: [Change the stored horizon](../../.tasks/app/UI-022-change-the-stored-horizon.md)

## Outcome

You can see your stored horizon on Home, open its date editor, and save a different date. Home then reads the resulting per day from the published snapshot. Cancelling or failing validation does not write a horizon.

UI-022 is To Do and ready. DATA-005, DATA-015, and UI-003 are Done. This document plans implementation; it does not start the task or claim its acceptance criteria are complete.

Follow CONTEXT.md, docs/spec/period-income-policy.md, and docs/state-and-validation.md. Keep budget arithmetic in computeBudget and use the existing month config API.

The snapshot contains horizonDate but no period identifier. Do not derive the edited period from horizonDate: a September horizon can be in October. Do not derive it from updatedAt either: that field records publication time.

## Interaction and ownership decisions

### Home and navigation

1. Render a Horizon row from snapshot.horizonDate in the ready Home view, beside the existing secondary figures. Keep per day as the largest figure.
2. Add a Change horizon action. The native Home route chooses the current local period at activation and opens /horizon?period=YYYY-MM.
3. Render no invented horizon in loading or error states. Offer editing from the ready view; retain Home's existing publication retry action.
4. Put route loading and navigation in src/app/horizon.tsx. Use a shared HorizonForm under src/ui/horizon for the input and submission behavior.
5. Supply horizon.web.tsx alongside the native route. Show the same controls using an explicit browser fixture and in-memory save behavior, consistent with the browser preview boundary.

### Date editor

Show a Change horizon heading, the selected period, a labelled Horizon input, a YYYY-MM-DD format hint, Save horizon, and Cancel. Explain that the date can extend beyond the selected period. Reuse Input, Button, safe-area handling, and existing visual tokens.

Use a text date input for this stage. It can reuse the existing controls without adding a native dependency. Choose a keyboard that permits hyphens; do not copy the money input keyboard. Keep the actions reachable with the keyboard visible and allow taps on them without an extra keyboard-dismissal tap.

Load the stored MonthConfig for the selected period. Seed the input once after that read succeeds. Show explicit loading, unavailable, and read-error states, with retry for recoverable reads. Do not substitute period end when a stored row is missing.

Keep field text in local React state. Model loading and form submission with discriminated unions. While saving, prevent duplicate submissions and disable editing and dismissal controls. Handle route removal during an outstanding save so a back gesture cannot masquerade as cancellation. Release that protection on success or failure.

On validation or write failure, keep the exact input and the editor open. Show field feedback for date errors and an actionable message for a failed write. Ignore late read results after navigation or a newer load. A background snapshot refresh must not remount the form or replace its input.

### Date rules

Use updateHorizonInputSchema.safeParse for field feedback and let updateHorizon validate again at the write boundary. Submit only period and horizonDate.

| Input for period 2026-09 | Result |
| --- | --- |
| 2026-09-01 | Valid, including when it is before today. |
| Today's date | Valid; render the engine's null per day behavior when daysToHorizon is zero. |
| 2026-09-30 | Valid period-end date. |
| 2026-10-15 or 2027-01-01 | Valid future date beyond period end. |
| 2026-08-31 | Reject because it precedes the period start. |
| Empty text, 2026-9-30, 2026-09-31 | Reject as malformed or impossible dates. |

Also cover February 29 in leap and non-leap years. Keep the date as a calendar string through validation and persistence. Do not apply manual transaction future-date validation or parse the field with new Date('YYYY-MM-DD').

### Period preparation and rollover

Keep the period in the route parameter. Validate it before reading and reject malformed or repeated parameters. For a route without a period, select currentPeriod from an injected local clock once and normalize the URL. Display that period so the save target is visible.

Pin that period for the editor session. If you open September just before October starts, Save still edits September's horizon. Never replace the target with currentPeriod at submission. The existing API permits explicit edits to stored historical horizons; the selected period's money totals and every unrelated config stay unchanged.

Use the existing root snapshot lifecycle for DATA-015 preparation. On a cold start or a rollover, coordinate the initial current-period read with completion of that preparation. If the row is absent while publication is loading, wait and retry the read after publication becomes ready. If preparation fails, expose its existing retry path. An absent historical period remains unavailable and must not be created by this editor.

Opening, typing, and cancelling call no mutation API. Automatic period preparation remains owned by the app lifecycle. Test cancellation against an already prepared ledger so its lack of writes is explicit. Do not copy preparation arithmetic into a route or invent opening totals.

After a rollover save, the publisher prepares and reads the actual current period. Home must display that period's snapshot, even if the editor just saved the previous period. Test this distinction directly.

### Save and publication

1. Validate and submit the pinned period and entered date to updateHorizon.
2. On database failure, preserve the form and allow retry. The existing concurrent-write error follows this path; do not retry it automatically.
3. On database success, return to Home. The month_config notification drives the existing publisher. Do not add a second refresh call after Save, compute an optimistic per day, or patch the snapshot store from the form.
4. Home shows the existing loading state until publication completes and then renders the exact published horizon and per day.
5. If the database commit succeeds but shared-storage publication fails, Home shows its publication error. Try again republishes committed data without repeating updateHorizon. A publication failure does not undo a saved horizon.
6. Saving the unchanged date may return successfully without a notification. Preserve that existing no-op contract; freshness remains the existing publisher's responsibility.
