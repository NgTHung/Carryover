## Product and data decisions

### Editable account details

1. Show the current account name, fixed bank or cash kind, current balance, and a Default label for bank. Account IDs, kind, and isDefault are read-only.
2. Provide Edit details and Reconcile actions on each account card. Edit details opens Name and Opening balance fields, with Save details and Cancel actions.
3. Initialize Opening balance from account.openingBalance, never account.balance. Keep its editable text as unformatted whole dong; format display-only amounts with formatVnd.
4. Save both fields in one operation. A failed opening balance validation cannot leave a renamed account behind.
5. Trim account names and reject blank names using the same policy as category and commitment names. Permit Unicode and duplicate display names; bank/cash labels distinguish the fixed identities. Add no arbitrary length or uniqueness rule.
6. Allow zero opening balance because the stored schema permits it. Reject negative values, fractional notation, exponent notation, separators, blank text, and unsafe integers. Reuse the currency constants and existing parsers; do not introduce rounding or currency scaling in the form.
7. Treat saving unchanged normalized details as a no-op: no account timestamp update and no account notification.
8. Opening balance editing creates no transaction. A routine correction uses the existing reconcile operation and remains visible as an adjustment in Transactions.

Place this explanation beside Opening balance:

> Your opening balance is what you held before recorded transactions. Changing it changes balances calculated from your ledger, including past balances. Saved period opening balances and reserves stay the same. To correct what you hold today, use Reconcile.

Show that explanation before Save. A separate confirmation dialog is unnecessary for this explicit edit form. Keep the default-account marker visible after any rename.

### Form state and navigation

Use a discriminated union for the active interaction: closed, editing details, saving details, reconciling, or saving reconcile. Retain only one active form on the screen so its account and operation are unambiguous. Require Save or Cancel before opening another form.

Keep draft text in local React state. Background account reads may update card balances but must not replace the text you are editing. Clear old success feedback when beginning another operation. Use account-specific accessible action labels so two cards do not produce indistinguishable controls.

Cancel and navigation away before Save discard the local draft without calling a mutation API. While a save is pending, guard duplicate submissions immediately, disable editing and dismissal actions, and protect route removal using the repository's existing navigation pattern. Ignore late read results after unmount or a newer request.

On validation or database failure, retain the exact input and show actionable feedback. A successful database save ends the editing operation. Model a subsequent refresh failure separately as saved-but-unavailable data, with a read retry. Do not offer another mutation as the remedy for a failed refresh.

Reuse Input, Button, visual tokens, keyboard inset handling, and scroll behavior. Save and Cancel must remain reachable with the keyboard visible. Keep the browser's current ledger-unavailable route for this task; component tests exercise the shared controls locally.

### Validated write boundary

Add editAccountDetails to the existing account API, accepting a strict object with accountId, name, and openingBalance. Infer its TypeScript input from the data schema. Reject identity, kind, default, deletion, and timestamp fields rather than silently accepting them.

Put the mutation orchestration in a new src/data/account-edits.ts module. Keep account-validation.ts as the schema owner and accounts.ts as the public facade. Factor the shared account update into this module so the existing updateOpeningBalance entry point and new details operation cannot develop different validation or notification policies. Preserve the existing updateOpeningBalance call shape for callers.

Add optional runAtomic and now injection to createAccountData without breaking its current database/notifier arguments. Supply nativeAtomicRunner from database.ts. Database tests use the existing asynchronous runner. Do not use an asynchronous callback with the synchronous driver's ordinary transaction method, or open nested top-level transactions.

For an actual details edit:

1. Validate the full input before database work.
2. Enter one atomic operation, read the active account, and reject missing or soft-deleted targets. Detect unchanged normalized values before performing writes.
3. Capture the local submission time once. Run prepareCurrentPeriodInTransaction on the same transaction connection before changing the opening balance. This fixes the new period's baseline against the ledger that existed before this edit.
4. Update only name, openingBalance, and updatedAt, with an active-row predicate and a checked returning result. Use a monotonic timestamp and the original timestamp in the write predicate to detect a stale write instead of reporting false success.
5. Read the resulting account balances through the existing projection logic before commit. Reject unrepresentable account or combined carryover balances with checked integer aggregation, so a valid individual amount cannot commit an unusable ledger total. Reuse existing money helpers; add no budget arithmetic here.
6. Commit, then emit accounts:edited once. If period preparation changed month_config, emit its matching notification after the same commit. No listener may observe a partially saved account or an uncommitted period.
7. On any failure, roll back the account and preparation changes and emit no mutation notification. Propagate the error with context.

An unchanged save need not prepare a period; startup, foreground, and snapshot refresh retain that responsibility. Existing stored opening balances, reserved totals, and horizons remain unchanged. Preparation may repair the current period's income total from actual income, but the account edit must never contribute to income or modify past configurations.

### Refresh and publication

Use the account notification as the invalidation source. Reload Accounts through its public read API and verify the mounted transaction list rereads renamed labels. Account choice screens must read current names when opened or refocused; update labels without resetting an unfinished transaction's fields or changing its selected account ID.

Subscribe and clean up at the route boundary. Follow existing route refresh patterns and keep the shared form independent of native database imports. Audit account name consumers before adding subscriptions; change only consumers that can remain stale after returning from Accounts.

The existing publisher responds to the committed notifications, prepares the actual current period, reads committed input, calls computeBudget, writes shared storage, and publishes that exact artifact to the app store. Do not call refreshBudgetSnapshot after Save or compute an optimistic carryover balance, discretionary, or per day in the form.

If shared-storage publication fails after a successful save, the account remains saved. Home shows its existing publication error. Its retry rereads committed data without repeating editAccountDetails or reconcileAccount. Multiple legitimate table notifications may queue multiple publications; test final consistency rather than assuming exactly one writer call per Save.
