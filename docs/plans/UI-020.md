# UI-020 execution plan

Revised on 2026-09-13 after reviewing the product contract and agreeing the [income and period policy](../spec/period-income-policy.md). This plan records future implementation. DATA-015 and UI-020 remain To Do until their implementation starts.

## 1. Complete DATA-015 first

Run taskroot validate, taskroot list, and taskroot context app:DATA-015 --format json. Start the ready prerequisite before changing production code.

Specify opening-balance and reserve derivation, first-launch behavior, missing historical periods, and any schema implications before writing the lifecycle service. Preserve actual-money semantics, historical snapshots, and the existing budget engine. Split schema or complex arithmetic work into separate passing commits under 500 changed lines.

Implement current-period preparation and atomic income maintenance at the data boundary. Cover transaction creation, edits, completion, soft deletion, direction changes, and dates moving between periods. Use the same boundary from existing editor routes. Prepare periods on startup, foreground refresh, and mutations that cross a local period boundary.

Verify first launch without seeded month config, mid-period opening, multiple periods away, idempotent retries, historical corrections, rollback, report consistency, and publication from committed data. Never derive income independently in a screen. Record evidence and complete DATA-015 only when its criteria pass.

Commit each coherent prerequisite stage with its tests. The final task-evidence commit is chore(tasks): complete DATA-015.

## 2. Extract shared transaction controls

Reload app:UI-020 context, verify readiness, and start it. Commit the lifecycle update as chore(tasks): start UI-020.

Add src/ui/transactions/transaction-form.ts and TransactionFormFields.tsx. Keep amount text and other form input local. Use expense and income variants for their different leaf and source fields. Reuse date-only helpers and the shared money schemas. Parse whole-dong text through the established range-checked BigInt path.

Creation requires a positive amount. Draft editing still accepts a blank amount as unknown. Keep create validation separate from draft validation while sharing controls. Refactor TransactionEditor.tsx without rewriting hidden payer or photo fields or deleted historical category references. Preserve draft completion and deletion behavior.

Defaults are bank, the local date when the form opens, no selected leaf, no quality, no note or source, payer you, and no photo. Validate the selected active account. Blank optional text becomes null. Changing direction clears fields forbidden by the new direction. A blank creation date uses the default; a supplied invalid or future date produces feedback.

Add tests/transaction-form.logic.test.ts and extend transaction-editor.component.test.tsx for unknown drafts, direction changes, local dates, invalid money, and hidden historical metadata.

Commit: refactor(ui): share transaction form controls.

## 3. Implement the creation route

Put loading, lifecycle, and navigation in src/app/transactions/new.tsx, with new.web.tsx beside it. A validated direction parameter selects expense or income. Invalid or repeated direction parameters stop before ledger reads; opening the bare route defaults to expense. Shared form presentation belongs in src/ui, following UI-009.

Expose a typed creation facade through src/ui/ledger-access.ts and its web counterpart. The native facade loads active accounts and category groups and invokes the DATA-015 transaction boundary. The web route explains that the ledger is available in the installed app and performs no database reads.

Load choices concurrently and show loading, failure, and retry states. Empty category choices do not prevent income creation. Expenses require an active leaf; search and inline category creation remain CAPTURE-004 work.

Model idle, saving, failed, and saved mutation states explicitly. Set a synchronous submission lock before awaiting the write. Disable Cancel and navigation away during the write. Before submission, Cancel writes nothing and leaves list filters unchanged. Failed writes retain every input. Successful commits keep insertion locked even if navigation fails.

Add tests/transaction-create.component.test.tsx and focused transaction-creation.database.test.ts coverage with this implementation. Exercise minimal expense and income, optional fields, invalid or future dates, missing leaves, failed writes, cancellation, and two immediate submit events producing one row.

Commit: feat(ui): add manual transaction creation.

## 4. Connect entry points and publication

Add Add expense and Add income actions to TransactionListView.tsx, including its empty state. Keep one primary action. Both links target the shared creation route with explicit direction parameters.

After a successful commit, atomically select the saved transaction's local period and clear category, account, and quality filters before returning to /transactions. Add the action to transaction-filters.ts and test it. Cancellation preserves prior choices.

Use existing ledger notifications for list, report, and snapshot refresh. The route never calls computeBudget or a snapshot writer. Test that income changes the current stored income total and account balance once, preserves the horizon, and leaves historical config unchanged.

Extend transaction-list.component.test.tsx and router-navigation.component.test.tsx for entry links, static route matching, invalid direction, migration gating, cold-start cancellation, and backdated creation visibility. Add publication-failure and navigation-failure tests proving that retry cannot insert another transaction.

Commit: feat(ui): connect transaction creation to ledger views.
