# UI-020 execution plan

Prepared on 2026-09-14 against the current transaction editor, transaction
list, route layout, and snapshot publisher. This plan implements
`app:UI-020`. It does not start the task.

## Current gate

UI-020 is not ready. `app:DATA-015` is still To Do and must be Done before
UI-020 starts. DATA-015 owns period preparation and the atomic transaction and
current-period income boundary. UI-020 must call that boundary. It must not
wrap the old transaction repository in a second income update.

At execution time:

1. Run `taskroot validate` and
   `taskroot context app:UI-020 --format json`.
2. Stop if DATA-015 is not Done. Complete DATA-015 under its own task and
   commits. Do not mix its implementation into UI-020.
3. Inspect the public mutation API delivered by DATA-015 and update only the
   provisional adapter names in this plan if needed. Preserve every behavior
   below.
4. Run the existing transaction logic, database, component, and route tests to
   establish a passing baseline.
5. Run `taskroot start app:UI-020`, validate, and commit only that lifecycle
   change as `chore(tasks): start UI-020`.

## Scope

UI-020 delivers one native creation route for complete expense and income
transactions, shared fields for creation and editing, list entry points, and
manual-date enforcement at the write boundary.

The task does not add photo capture, category search, inline category creation,
reserve payment workflows, expected income, recurring income, payday fields,
automatic horizon changes, or browser ledger access. Those belong to later
tasks. It also does not add budget arithmetic or another snapshot refresh
service.

## Ownership and data flow

Keep each concern at its existing boundary:

| Concern | Owner |
| --- | --- |
| Direction route parameter and route loading | `src/app/transactions/new.tsx` |
| Browser refusal | `src/app/transactions/new.web.tsx` |
| Controlled fields and field feedback | `src/ui/transactions/TransactionFormFields.tsx` |
| Form defaults, parsing, direction cleanup, and payload construction | `src/ui/transactions/transaction-form.ts` |
| Creation mutation state and submit lock | `src/ui/transactions/TransactionCreator.tsx` |
| Manual date rule and active stored references | The DATA-015 write boundary, with a small manual policy adapter if needed |
| Native composition | `src/ui/ledger-access.ts` |
| Browser fail-closed composition | `src/ui/ledger-access.web.ts` |
| Selected period and filters | `src/ui/transactions/transaction-filters.ts` |
| Ledger, current-period income, and notification | SQLite through the DATA-015 boundary |
| Budget figures and publication retry | The existing snapshot publisher |

The successful flow is:

1. Parse the route direction before requesting ledger choices.
2. Read active accounts and active category groups concurrently.
3. Initialize local form text with the default bank account and current local
   date. Do not select a leaf or quality.
4. Validate fields for immediate feedback.
5. Acquire a synchronous submit lock.
6. Call the DATA-015 mutation boundary once with a complete transaction.
7. Commit the transaction and any current-period income change atomically.
8. Emit the existing committed ledger notification.
9. Select the saved transaction's period and clear all list filters in one
   Zustand update.
10. Return to `/transactions` without waiting for snapshot publication.

## Stage 1: Add the manual-write policy

### Date helpers

Extend `src/data/date-only.ts` with pure helpers instead of keeping date parsing
inside `TransactionEditor.tsx`:

- Convert a valid `DateOnly` into a local `Date` while preserving the time of a
  supplied anchor. Creation uses the time at which the form opened. Editing
  uses the transaction's existing time.
- Compare two validated date-only strings as local calendar values.
- Keep `dateOnlyFromLocalDate` as the formatter used for today.
- Reject impossible dates through `dateOnlySchema`. Never parse
  `YYYY-MM-DD` through UTC.

Add focused cases to `tests/transaction-validation.logic.test.ts` or a small
`tests/manual-transaction-validation.logic.test.ts` for leap days, invalid
calendar dates, same-day values, and tomorrow across a local midnight.

### Write-boundary contract

Add a small clock-aware manual transaction policy beside the DATA-015
transaction service. Use the final DATA-015 name rather than introducing a
parallel repository. Inject `now: () => Date` for deterministic tests and use
`new Date()` only in native composition.

The boundary must enforce these rules for manual create, edit, and draft
completion:

- The resulting occurred date is today or earlier in the local calendar at
  submission time. A later clock time on the same local date is valid.
- Create accepts only `status: 'complete'` with a positive whole-dong amount.
- Expense requires an active leaf. Income requires `categoryId: null`.
- The chosen account is active when the write occurs. Loading active accounts
  in the screen is not enough because an account can change before submit.
- Expense and income use `adjustmentEffect: null`.
- Optional blank note and source text become null.
- Income alone may carry a source label.
- Creation sets payer to you and photo to null.

Validate the date before a write. Keep the active account, active leaf, ledger
mutation, and current-period income maintenance inside the same SQLite
transaction supplied by DATA-015. A failed validation or database operation
must change no row and emit no notification.

Editing and draft completion must validate the resulting occurred date, even
when the date field was not changed. Restore remains on its versioned import
boundary and must not inherit this manual-entry rule.

If DATA-015 already exposes the exact policy, add no wrapper. Bind the UI facade
directly to it. If it exposes only generic mutations, add one manual adapter
that delegates exactly once after validation. Do not perform a separate
`month_config` update from the adapter or screen.

### Database evidence

Extend `tests/transactions.database.test.ts` for the shared edit and completion
regressions, and add `tests/transaction-creation.database.test.ts` for the
manual boundary. Prove:

- Minimal expense and income payloads round-trip with integer amounts.
- Expense rejects a null, group, deleted, or unknown category.
- Both directions reject a deleted or unknown account at write time.
- Today and past dates commit. Tomorrow rejects for create, edit, and complete.
- Rejected writes leave the transaction, current-period income, and notifier
  unchanged.
- A current-period income create changes the stored actual income exactly once.
- A historical income create leaves every past stored money total unchanged.
- Income creation changes no horizon, opening balance, or reserve total.
- Failure between the transaction and income operations rolls back both.

Commit this stage with its tests as
`feat(data): enforce manual transaction write policy`.

## Stage 2: Extract shared form logic and controls

### Pure form module

Create `src/ui/transactions/transaction-form.ts`. Keep it free of React,
navigation, SQLite, and snapshot imports. Define:

- `EditableTransactionDirection` as `expense | income`.
- `TransactionFormValues` with text for amount, date, note, and source label,
  plus direction, account id, leaf id, and nullable quality.
- `TransactionFormErrors` with separate amount, date, account, leaf, and form
  errors.
- A creation initializer receiving direction, active accounts, and an injected
  current date.
- An editor initializer receiving the stored transaction.
- A direction transition that clears category when moving to income and clears
  source label when moving to expense.
- A validator for create, complete edit, and draft edit modes.
- A complete-create payload builder.
- An edit change builder that returns only fields whose values changed.

The creation initializer must select the active default bank account. Treat a
missing or ambiguous default as an explicit load error instead of choosing the
first row. It must leave amount blank, leaf null, quality null, note blank, and
source blank. The date is the local calendar date at form initialization.

Parse amount text with `positiveVndInputSchema` for creation and complete
transactions. Draft editing continues to use `draftVndInputSchema`, so blank
still maps to null. The BigInt range check must occur before conversion to a
JavaScript number. No floating-point intermediate may hold money.

The edit change builder is a required regression boundary. It must not include
unchanged `photoKey`, payer, or category fields. This preserves hidden capture
metadata and historical references to leaves that are no longer active.

### Controlled presentation

Create `src/ui/transactions/TransactionFormFields.tsx` as a controlled
component. It renders:

- Amount with number-pad input and field error.
- Expense and income choices.
- Active leaf choices for expense, with an inline leaf error.
- Source input for income.
- Active account choices, with an inline account error.
- Optional quality choices with no preselection.
- Date with its field error.
- Optional note.

Every input and choice receives a disabled state. The component owns no write,
route, or snapshot behavior.

### Editor refactor

Refactor `src/ui/transactions/TransactionEditor.tsx` to use the pure form module
and shared fields. Keep its draft completion, edit, delete confirmation,
read-only adjustment, and read-only transfer behavior unchanged.

Use the manual DATA-015 mutation methods through
`src/ui/transactions/transaction-editor-contract.ts`. Add a synchronous ref
guard to edit, completion, and delete actions so two events in the same render
cannot issue two writes. Keep inputs intact on failure and show date feedback
at the Date input.

Extend `tests/transaction-editor.component.test.tsx` to prove:

- An unknown draft still opens with blank amount and saves as null.
- A draft completes only with a positive amount and, for expense, an active
  leaf.
- A future date is rejected with Date field feedback.
- Direction changes clear fields forbidden by the new direction.
- Editing another field does not send hidden photo, payer, or unchanged
  historical category fields.
- Failed edits retain every visible value.
- Two immediate save events call the boundary once.

Add `tests/transaction-form.logic.test.ts` for defaults, amount bounds, local
date conversion, direction transitions, trimmed optional text, create payloads,
and changed-field payloads.

Commit this stage as `refactor(ui): share transaction form controls`.

## Stage 3: Build the creation component and facade

### Typed facade

Create `src/ui/transactions/transaction-create-contract.ts` with the smallest
surface the route needs:

- `listActiveAccounts()`.
- `listActiveCategoryGroups()`.
- The DATA-015 manual complete-transaction create operation.

Expose one stable instance through `getTransactionCreateData()` in
`src/ui/ledger-access.ts`. Add the same export to
`src/ui/ledger-access.web.ts`, where it must throw the existing browser refusal
if called. Do not export or call `computeBudget`, a snapshot writer, or a new
refresh operation from the create facade.

### Creation component

Create `src/ui/transactions/TransactionCreator.tsx`. It receives loaded choices,
initial direction, an injected initialization date, the create facade, Cancel,
the committed callback, and a synchronous write-pending callback.

Model its mutation state as a discriminated union:

- `idle` accepts edits and submission.
- `saving` disables every input, Cancel, and submit.
- `failed` shows the boundary error without resetting the form.
- `saved` holds the returned transaction and cannot submit again.

Also keep an in-flight ref. Set it before the first await and return immediately
when it is already set. React's disabled state alone is not a duplicate-write
guard. Call the write-pending callback immediately when the ref changes so the
route can block removal without waiting for a render. Clear the pending state
after a failed write. After a successful commit, release route removal, retain
the saved transaction, and never reopen submission.

Treat post-commit work separately from the mutation promise. If the committed
callback fails, keep the `saved` state and expose a navigation-only retry that
receives the stored transaction. Never turn a navigation failure into `failed`
mutation state and never clear the submission lock.

Build exactly one create payload:

- `status: 'complete'`.
- Parsed positive integer amount.
- Selected active account.
- Expense leaf or income null category.
- Optional quality and note.
- Optional income source label.
- `payer: { kind: 'you' }`.
- `photoKey: null`.
- `adjustmentEffect: null`.
- Parsed local occurred date.

Add `tests/transaction-create.component.test.tsx` for defaults, minimal and full
expense, minimal and full income, blank optional text, invalid money, missing
leaf, invalid and future dates, failed writes, retained input, Cancel, disabled
controls, and immediate duplicate events.

Commit this stage as `feat(ui): add manual transaction creation form`.

## Stage 4: Add native and web routes

### Route parsing

Add creation-route parsing to
`src/ui/transactions/load-transaction-route.ts`, or rename that module only if
the resulting API is clearer and all imports move in this commit.

The parser accepts `expense`, `income`, or no direction. No direction defaults
to expense. Any other string and every array value, including repeated query
parameters, is invalid. Return a discriminated result rather than falling back.

Extend `tests/transaction-route.logic.test.ts` to prove every accepted and
rejected shape. Invalid parsing must occur before either choice reader is
called.

### Native controller

Create `src/app/transactions/new.tsx`. Keep loading, retry, navigation, and the
write-navigation lock in this route.

For a valid direction:

1. Load active accounts and active category groups concurrently.
2. Render explicit loading and retryable error states.
3. Allow income creation when the category result contains no leaves.
4. Render `TransactionCreator` after both reads succeed.
5. Disable Cancel and prevent back, swipe, or programmatic route removal only
   while the write promise is unresolved. Use the current Expo Router
   navigation event API. Do not add a navigation dependency.

Keep a route ref as the source for the route-removal guard. Update it through
the creator's synchronous write-pending callback. Release navigation only after
the data promise has either failed or returned a committed transaction. This
prevents the route's own successful redirect from being blocked by a delayed
React render.

Cancel performs no mutation. If router history exists, go back. On a cold-start
direct link, replace with `/transactions`. Either path leaves the existing
Zustand period and filters unchanged.

Before wiring the committed callback, add one atomic action to
`src/ui/transactions/transaction-filters.ts`, named for its behavior, such as
`revealTransaction(occurredAt)`. It derives the local period from the saved
transaction date, selects that period, and clears category, account, and
quality filters in one Zustand update.

After commit, call `revealTransaction` and then replace with `/transactions`.
Wrap navigation separately from the mutation. If navigation throws after
commit, render a saved state with a `Back to transactions` retry. That retry
performs the idempotent filter update and navigation only. It must never call
create again.

### Web controller

Create `src/app/transactions/new.web.tsx`. It uses the same direction parser.
An invalid link shows the invalid-route state. A valid link explains that the
ledger is available only in the installed app. It must not import
`ledger-access` or request accounts, categories, migrations, or transactions.

Extend `tests/router-navigation.component.test.tsx` for:

- Expense, income, and bare native routes.
- Invalid and repeated direction parameters before ledger reads.
- Migration gating on the direct route.
- Loading failure and retry.
- Cold-start cancellation.
- Route removal while saving.
- A committed write followed by navigation failure and navigation-only retry.
- The web route remaining outside the ledger boundary.

Extend `tests/transaction-list.logic.test.ts` in this stage to prove the reveal
action selects the saved local period, clears every filter, and produces one
observable Zustand update.

Commit this stage as `feat(app): route manual transaction creation`.

## Stage 5: Connect the transaction list

Use the `revealTransaction` action added with the route. Do not use the existing

Add `Add expense` and `Add income` links to the header in
`src/ui/transactions/TransactionListView.tsx`. Expense is the single primary
action and income is secondary. Because the header renders when the list is
empty, both actions remain reachable with zero rows and with active filters.
Use the shared route with explicit direction parameters.

Extend `tests/transaction-list.component.test.tsx` to prove:

- Backdated creation becomes visible after returning to the list.
- Cancel preserves the prior period and filters.
- Both entry actions exist in normal, empty, and filtered-empty flows.
- Each action links to the correct direction on the shared route.
- Existing committed notifications still reload rows and filter choices.

The route must not request a list refresh directly. The committed transaction
notification remains the refresh trigger for the list, reports, and snapshot
publisher.

Commit this stage as `feat(ui): reveal newly created transactions`.
