# UI-023 execution plan

Date: 2026-09-15

Task: [Record transfers between bank and cash](../../.tasks/app/UI-023-record-transfers-between-bank-and-cash.md)

## Outcome and readiness

You can open Record transfer from Accounts, choose which account sends money and which receives it, enter whole-dong money and a local date, and save. Transactions shows one transfer with a read-only detail screen identifying both accounts. The source balance decreases and the destination balance increases by exactly the same amount. Spending, income, and the combined carryover balance retain their values.

UI-023 is To Do and ready. Its dependencies, DATA-002 and UI-001, are Done. UI-024 and UI-033 are also Done and supply the current Accounts controls and refresh recovery. Planning does not start implementation or check acceptance criteria. BUILD-005 owns release-wide iPhone verification.

Use CONTEXT.md for vocabulary, docs/state-and-validation.md for ownership, and docs/spec/period-income-policy.md for stored period behavior. Prefer the implemented period preparation over stale statements in documentation that describe DATA-015 as pending.

## Product decisions

### Creation flow

1. Add Record transfer to Accounts. Open /transfers/new. Disable this action while account details or reconcile is active, a write is pending, or account data is unavailable after a failed refresh. Preserve the existing read retry.
2. The new route reads active accounts through its injected public data contract. Show a retryable read error if loading fails. If either fixed account is unavailable, explain that two active accounts are required and offer return navigation.
3. Default From to the active default bank account and To to cash. Resolve identities by ID, kind, and default marker, never by display name. Do not choose arbitrary accounts if the fixed pair is missing or ambiguous.
4. Let you select either direction through labeled From and To controls. Keep the two selections distinct. With two accounts, choosing the current destination as the source swaps the pair. Show account kind beside the current name so duplicate names remain understandable.
5. Show Amount in VND and Date as YYYY-MM-DD. Amount starts blank. Date starts at the local date when the form opens. Use Record transfer and Cancel actions. Show: Moving money between your accounts does not count as spending or income.
6. Parse amount text through positiveVndInputSchema, then validate the final RecordTransfer payload. Reject blank, zero, negative, fractional, exponent, separator, nonnumeric, and unsafe values without rounding or truncation. Accept 1 VND and the safe maximum only when the resulting account balances remain representable.
7. Accept today and earlier local dates. This plan extends the existing manual-entry date policy to manually recorded transfers because this flow records money already moved. Scheduling is outside this task. Enforce the rule at the write boundary as well as the form, using the shared assertManualOccurredAt helper and an injected submission clock. Update the policy document to state this extension explicitly.
8. Reuse dateOnlySchema and localDateFromDateOnly with a stable form-open anchor. Compare local calendar dates, not UTC strings or exact timestamps. A later time on today is valid. Invalid calendar dates and tomorrow are rejected. Backdated transfers appear in their recorded period and affect the live account projection.
9. Preserve the existing ability to record a transfer that makes the source balance negative. The ledger records what happened; there is no existing insufficient-funds rule. The transfer amount remains positive, and each derived balance must stay within the signed safe range.
10. After a committed save, close the form and return to Accounts. Its existing transfers subscription refreshes balances. Read or publication failures after commit expose read/publication retry, never a second transfer submission. Do not require recordTransfer to return an ID just to navigate after creation.

Creation has no category, quality, income source, split, reserve payment, photo, or note fields. Transfer editing, deletion, scheduled transfers, account creation, and legacy migration are outside this task.

### Form state and recovery

Use separate load and submission discriminated unions. Submission distinguishes editing, saving, and saved, with draft text carried only where needed. Keep an immediate ref guard as well as rendered pending state so two taps before a render call recordTransfer once.

Cancel and back navigation before Save discard the local draft and call no mutation API. During a pending write, disable fields, account switching, Save, and Cancel, and prevent route removal using the existing navigation guard. If the write rejects, retain the exact amount, date, and account choices and show the error with a retry action.

Refresh account labels when the creation route refocuses or receives an accounts notification. Preserve typed fields and selected IDs across reads. If a selected account becomes inactive, block Save with an explicit unavailable-account message; do not silently redirect the transfer. Recheck account activity inside the write transaction even if the UI data looked current.

Guard asynchronous reads against unmount and newer requests, unsubscribe on cleanup, and preserve UI-033 behavior when reads fail. A successful write permanently leaves submission state even if navigation, Accounts refresh, or snapshot storage later fails. If the form remains mounted after such a failure, show Transfer recorded with a return/read retry action and no repeat Save.

Use Input, Button, current visual tokens, a scrollable keyboard-aware form, and accessible labels. Save and Cancel must remain reachable while the keyboard is open. Keep the browser routes explicit about ledger availability; shared component tests provide the local interaction loop.

### Transfer details and list behavior

Add /transfers/[transferId] for dedicated transfers. Validate a scalar UUID before any database read. Missing parameters, repeated parameters, malformed IDs, unknown IDs, and soft-deleted transfers produce explicit invalid or unavailable states. Read errors offer a retry. Keep a return-to-Transactions action for direct links with no back history.

Show Transfer, the positive formatted amount, From name and kind, To name and kind, and local occurred date. Repeat the spending/income explanation. Provide no edit or delete controls.

Read current account labels using the same projection as the list. Retain labels for soft-deleted accounts referenced by a surviving transfer, consistent with existing history behavior. Subscribe to transfers and accounts changes and reread on focus. Ignore obsolete responses when the route ID changes or the component unmounts.

For TransactionListRow variants:

| Variant | Navigation |
| --- | --- |
| kind transfer, source transfers | Open /transfers/[transferId], with an accessible label naming both accounts. |
| kind transfer, source transaction | Keep the existing read-only legacy row. It stores one account and cannot truthfully provide the second account. Do not guess a pair or pass its ID to the dedicated transfer reader. |
| kind transaction | Preserve existing expense/income editor and adjustment detail routes. |

Preserve period sorting and filters. A dedicated transfer is visible under either participating account filter and hidden when category or quality filters exclude it. Returning from a detail screen preserves the selected period and filters. The detail read must not depend on the current list filter or require loading the whole period.

## Data boundary and module design

### Atomic write

Put transfer mutation orchestration in src/data/transfers.ts and delegate recordTransfer from createAccountData. Reuse the existing options runner and clock; if its AccountEditOptions name becomes misleading, move the shared option type to a small account-data-options module and preserve existing call shapes.

For each write:

1. Parse the strict recordTransferSchema before database access. Validate the local occurred date against one captured submission time.
2. Enter the injected atomic runner. Read and require both distinct active accounts on the transaction connection.
3. Insert exactly one transfers row. Store a positive integer amount; source and destination determine the effects. Create no transactions rows and change no account opening balances or identity fields.
4. Read resulting account balances through readAccountBalances on the same connection before commit. Its BigInt projection rejects overflow or underflow of either account. Roll back the insertion if projection fails. Do not duplicate subtraction in the form or add another budget calculation.
5. Commit, then emit transfers:created once. Failed validation, inactive accounts, insertion errors, projection errors, or transaction failure emit no transfer notification and persist no transfer.

Use the native exclusive runner already supplied in database.ts. Tests use the existing asynchronous runner. Do not place an asynchronous callback in the native synchronous driver's ordinary transaction method or start a nested top-level transaction.

This transfer moves money between two active accounts, so it does not change their combined balance or actual income. Keep period preparation in the existing publication path. It may initialize the actual current period after rollover, but must not rewrite stored historical configuration or attribute transfer money to income. Test this ordering rather than adding unnecessary month_config writes to recordTransfer.

### Shared detail read

Add src/data/transfer-reads.ts with the dedicated transfer projection and account label resolution shared by list and detail. Keep reusable transfer read types with this module and preserve existing transaction-list type exports where callers rely on them. Avoid a runtime cycle between the list and transfer modules.

Expose readTransfer(transferId) through createAccountData, delegating to transfer-reads.ts, with a typed result containing transfer, fromAccount, and toAccount, or undefined. The public method validates the ID, hides a soft-deleted transfer, and resolves both account labels without filtering historical account references. Extract the existing dedicated transfer list query into the same module; preserve ordering and filter semantics in transaction-list.ts.

Add src/ui/transfers/transfer-data-contract.ts with separate creation and detail contracts. Creation needs listActiveAccounts and recordTransfer. Details needs readTransfer. Native ledger-access composes these from real data APIs; its web counterpart exports unavailable fallbacks. Shared UI modules import types and pure helpers, never the native database.

Use src/ui/transfers/transfer-form.ts for initialization, direction changes, and validated payload construction. Use TransferForm.tsx for controls and TransferDetail.tsx for detail rendering. Keep loading, focus refresh, route parameters, subscriptions, and removal protection in src/app/transfers/new.tsx and [transferId].tsx, with matching .web.tsx routes. Extract small route validation helpers when needed for isolated tests.

| Reports | Compare public month-summary and period-history output before/after, including income, spending, category/quality totals, and daily figures. Use fixtures with real expenses, income, splits, and an unknown draft so exclusion is tested against nonempty data. |
| Snapshot | Compare all financial fields at a fixed clock and horizon, excluding publication metadata. Carryover balance, discretionary, per day, runway, and unknown count retain their values. The writer artifact equals the ready app-store artifact. |
| Stored period isolation | Existing current and past month_config money fields and horizon stay fixed when actual income is already synchronized. A backdated transfer does not rebuild past config. |
| Rollover | Save after the local period changes and current config is missing. Existing publication preparation opens the actual current period once. A transfer contributes no income and preserves the prior period. |
| Publication failure | Fail shared-storage writing after commit. The transfer persists and the snapshot store shows its existing error state. Publisher retry succeeds without a second mutation. |
| Restart | Close and reopen the same database. Balances, transfer details, list membership, stored positive amount, unchanged report totals, and a fresh published snapshot agree with the pre-close state. |

A fixed-clock comparison matters: a real date change can change per day or runway independently of a transfer. Tests must separate lifecycle effects from the transfer's financial effect.
