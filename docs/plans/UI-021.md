## Decisions fixed by this plan

These rules remove ambiguity before implementation:

1. A commitment amount is a reserve, not proof of an expense. Starting a
   payment leaves the transaction amount blank so you must enter what moved.
2. A due date is not a payment date. Payment creation defaults to today's local
   date and never copies the commitment due date into `occurredAt`.
3. A payment started from a selected period must use an occurred date in that
   period. This makes the new expense clear the reserve the screen says it will
   clear. A future period cannot accept a payment because manual transactions
   reject dates after today.
4. A reserve payment is a complete ordinary expense. Its direction and reserve
   leaf stay fixed, while amount, account, date, quality, and note use the shared
   transaction controls.
5. Payments have no commitment foreign key. The existing category and period
   matcher remains the only authority for which commitment a payment clears.
6. Duplicate commitments that use one reserve leaf clear by due date and then
   commitment ID. Only the next unpaid commitment for that leaf gets a Record
   payment action. This prevents an action on a later duplicate from claiming
   it will clear that exact row.
7. The commitment screen is an operational view of live commitments and
   payments for a selected period. It is not a reconstruction of historical
   month config inputs.
8. Commitment changes and reserve payments publish through the existing
   committed ledger notifier. No screen calls budget arithmetic, writes a
   snapshot, or edits month config.
9. A committed expense remains saved if navigation or snapshot publication
   fails. Navigation retry never repeats the transaction mutation.
10. Payment eligibility is checked again in the same atomic SQLite transaction
    that inserts the expense. A route-level read is presentation data only and
    cannot authorize a later write.

## Scope

UI-021 delivers:

- A native Settings route that lists all non-deleted commitments.
- Create, edit, deactivate, reactivate, and confirmed soft-delete actions.
- Name, positive integer VND amount, due day, and active reserve leaf fields.
- A selected-period view of paid and unpaid commitment status, with an exact
  safe unpaid total or an explicit overflow state produced by the data layer.
- A reserve-payment intent in the shared UI-020 transaction creation route.
- A Settings entry point from Home and a fail-closed browser route.
- Logic, real SQLite, component, route, and snapshot publication evidence.

This task does not add recurring transactions, automatic expenses, reminders,
notifications, commitment history rows, partial commitment payments, payment
amount matching, a new Settings information architecture, or category creation
inside the commitment form. It does not alter the commitment schema or add a
database migration unless execution discovers a proven data requirement that
must first be recorded as separate task scope.

## Ownership and data flow

Keep each concern at one boundary:

| Concern | Owner |
| --- | --- |
| Commitment input validation | `src/data/commitment-validation.ts` and a pure UI form adapter |
| Payment-to-commitment ordering | `src/data/commitment-reserves.ts` |
| Consistent commitment and payment read | `src/data/commitments.ts` |
| Active reserve leaf choices | `src/data/categories.ts` through the UI facade |
| Commitment form state and payloads | `src/ui/commitments/commitment-form.ts` |
| Commitment cards and confirmation controls | `src/ui/commitments/` components |
| Selected period, loading, subscriptions, and route parameters | `src/app/settings/commitments.tsx` |
| Browser refusal | `src/app/settings/commitments.web.tsx` |
| Reserve-payment route intent | `src/ui/transactions/load-transaction-route.ts` |
| Shared payment fields and submit lock | `src/ui/transactions/TransactionCreator.tsx` |
| Atomic payment eligibility and expense write | A narrow reserve-payment data boundary that reuses UI-020's transaction-scoped complete-create logic |
| Current period preparation | DATA-015 through existing publication and mutation paths |
| Budget figures and snapshot write | The existing snapshot publisher and `computeBudget` |

A commitment mutation follows this flow:

1. Validate local form text for field feedback.
2. Acquire a synchronous mutation lock before the first await.
3. Call one existing commitment data mutation.
4. Let the data boundary validate the active reserve leaf at write time.
5. Commit the commitment change and emit one committed notification.
6. Reload the selected-period overview and active reserve leaf choices.
7. Let the existing publisher reread current committed inputs and write the
   next snapshot.

A reserve payment follows this flow:

1. Open the shared transaction creation route with a validated payment intent,
   commitment ID, and selected period.
2. Read accounts, active categories, and the selected-period commitment
   overview before initializing the form.
3. Confirm for presentation that the target is active, unpaid, next for its
   reserve leaf, and still points to an active reserve leaf.
4. Initialize a complete expense with blank amount, today's local date, the
   default bank, and the fixed reserve leaf.
5. Validate that the entered date is today or earlier and belongs to the
   selected period.
6. Acquire the existing synchronous submit lock and call the reserve-payment
   mutation once with the payment intent and complete expense payload.
7. In one atomic SQLite transaction, reread the commitment and competing
   payments, verify that the target is still eligible, and insert through the
   shared UI-020 complete-transaction logic. A commitment or payment write
   cannot interleave between that check and insertion.
8. Commit one expense and emit the existing transaction notification.
9. Return to the same commitment period. The reloaded overview applies the
   deterministic matcher and shows the new paid and unpaid states.

## Stage 1: Expose deterministic period status

### Pure matching result

Refactor `src/data/commitment-reserves.ts` so the existing ordering produces a
reusable match result instead of only a number. Use a discriminated union:

- `paid` contains the commitment and the one matched payment.
- `unpaid` contains the commitment and no synthetic payment fields.

The pure matcher must:

- Sort copies of the inputs. Never mutate caller-owned arrays.
- Order commitments by resolved due date, then commitment ID.
- Group payments by reserve leaf and order them by occurred timestamp, then
  transaction ID.
- Consume at most one payment for each active commitment and at most one
  commitment for each payment.
- Ignore amount equality because the reserve can differ from the charge.
- Return matches in stable commitment order.

Keep one pure unpaid-total reducer over the unmatched results. It must accumulate
with `bigint` and return a discriminated result: `available` contains the safe
integer VND amount and `overflow` contains no fabricated amount. Keep
`calculateUnpaidReserve` as the public number-returning function used by the
budget path; implement it by unwrapping that result and throwing the existing
safe-bound error on overflow. The overview consumes the result directly so an
oversized aggregate cannot hide the rows needed to correct it. Do not add a
second total or matcher in UI code.

Extend `tests/commitment-reserves.logic.test.ts` first. Cover reversed input,
tied dates, tied timestamps, duplicate reserve leaves, extra payments, different
payment amounts, immutability, and safe-total overflow. Assert exact matched
transaction IDs so deterministic behavior is observable.

### Selected-period overview

Add a screen-oriented read model to `src/data/commitments.ts`, named by its
outcome, such as `readCommitmentOverview(period)`. Return:

- The validated period.
- The shared unpaid-total result, either an exact safe amount or `overflow`.
- Every non-deleted commitment in stable due-day, name, and ID order.
- Its resolved due date for the selected period.
- Its active or inactive state.
- For active rows, a `paid` result with the matched transaction ID or an
  `unpaid` result with whether it is next to accept a payment for its leaf.
- A reserve leaf reference with its stored name and group name when those rows
  still exist, plus whether that leaf is currently active.

Use a nested discriminated union for inactive, paid, and unpaid states. Do not
represent them as optional booleans and nullable IDs that can contradict each
other.

Read non-deleted commitments, their stored category references, and complete
expense candidates for the selected period from one SQLite statement. This
preserves DATA-009's consistent-view rule for both the aggregate and row status.
Do not read month config, create missing configuration, or infer payment from a
due date. The existing `readReservedUnpaid(period)` may delegate to the same
private read and pure matcher, but its public return type stays unchanged for
the snapshot source. Its overflow behavior also stays unchanged. Only the
screen overview remains usable in that state.

Keep `readCommitments()` for existing callers. Give it stable ordering if the
new overview shares that helper. Do not include soft-deleted commitments in the
screen overview. Keep inactive commitments visible because they must be
reactivatable.

### Real SQLite evidence

Extend `tests/commitments.database.test.ts` before changing persistence code.
Prove:

- The overview rejects malformed periods before querying.
- A new active commitment appears as unpaid without creating a transaction.
- Inactive commitments remain in management results but reserve nothing.
- A soft-deleted commitment disappears and its historical expense remains.
- One complete expense clears one commitment in the same period and leaf.
- Drafts, income, transfers, adjustments, deleted expenses, other leaves, and
  expenses outside the selected period clear nothing.
- The paid result identifies the exact deterministic payment.
- Duplicate leaf commitments clear by due date and ID regardless of row order.
- A day 29, 30, or 31 clamps within the selected period.
- A deleted category reference remains displayable as unavailable, while it
  cannot be chosen for a new active commitment.
- The row statuses and unpaid total come from one real database view during an
  overlapping write.
- An aggregate beyond the safe VND bound returns all management rows with an
  overflow total state, while `readReservedUnpaid(period)` still rejects it.

Commit this stage with its tests as
`refactor(data): expose commitment period status`.

## Stage 2: Add pure commitment form rules

Create `src/ui/commitments/commitment-form.ts`. Keep it free of React,
navigation, SQLite, and snapshot imports. Define:

- Text values for name, amount, and due day.
- A nullable reserve leaf ID.
- Separate field errors for name, amount, due day, leaf, and form failure.
- A creation initializer with blank text and no preselected leaf.
- An edit initializer that preserves the stored commitment values.
- A validator and builders for create and changed-field edit payloads.

Parse amount with `positiveVndInputSchema`. Keep the input as text until that
schema returns a safe positive whole-dong number. Never pass it through
`parseFloat`, arithmetic, or a floating-point intermediate. Parse due day as a
base-10 integer only after rejecting blank, decimal, signed, and non-digit text,
then validate with `commitmentDueDaySchema`.

Derive reserve leaf choices from active groups whose kind is `reserve`. Leave
spend leaves out even though the persistence boundary will reject them again at
write time. If no active reserve leaf exists, show an explicit prerequisite and
a link to Categories. Do not silently select the first leaf.

An edit payload includes only changed name, amount, due day, and leaf fields.
Activation stays a separate explicit action. Show an unavailable historical
leaf on the stored commitment. An inactive commitment may change name, amount,
or due day without replacing that leaf. Changing its leaf or reactivating it
requires a currently active reserve leaf. Any edit that leaves a commitment
active also requires a currently active reserve leaf, so an active commitment
whose stored leaf became unavailable must select a replacement before saving.
These rules mirror `editCommitment` instead of allowing a form submission that
the persistence boundary must reject.

Add `tests/commitment-form.logic.test.ts` for:

- Blank creation defaults and edit initialization.
- Name trimming.
- Positive integer VND bounds, including values beyond the safe limit.
- Due days 1 and 31, with rejection of 0, 32, decimals, signs, and whitespace-
  only input.
- Reserve-only leaf selection and no implicit default.
- Minimal create payloads.
- Changed-field edit payloads that omit unchanged fields.
- Stored unavailable leaf presentation without treating it as selectable.
- Active and inactive edits with an unavailable stored leaf, including the
  required replacement for any result that stays or becomes active.

Commit this stage as `feat(ui): define commitment form rules`.

### Components

Create small modules under `src/ui/commitments/` rather than growing one screen
past the repository size target:

- `CommitmentForm.tsx` renders controlled name, amount, due-day, and reserve-
  leaf fields with inline errors.
- `CommitmentCard.tsx` shows the name, reserve amount, due day, leaf, active

- `UnpaidReserveList.tsx` shows the selected period, the data-owned unpaid

Use `formatVnd` only for display. A component must never sum commitment amounts.
Explain deactivation and deletion before the action:

- Deactivation stops the commitment from reserving money but keeps it available
  to reactivate.
- Soft deletion removes it from Settings without deleting any transaction.

Use a discriminated form and mutation state. A synchronous ref must acquire the
write lock before the first await so rapid repeated events cannot issue two
writes. While a mutation is pending, disable all conflicting edits, period
changes, Cancel, delete confirmation, and payment navigation. A failed write
keeps the form values and confirmation context. A successful write closes only
the completed form and reloads committed data.

Do not add an Undo action because the data API has no restore mutation. Do not
call transaction creation from a deactivate or delete handler.

- Concurrent overview and reserve-leaf loading.
- Request IDs or cancellation guards so a slow old-period read cannot replace a

- Retryable load failures.
- Subscription to committed `commitments`, `transactions`, and `categories`

Use the shared `PeriodSelector`. Allow past, current, and future period views.
Disable Record payment for a future selected period and explain that a due date

route. DATA-015 and the snapshot publisher own current period preparation.

## Stage 4: Extend the shared creation flow for reserve payments

### Route intent

Extend `src/ui/transactions/load-transaction-route.ts` with a discriminated
creation intent:

- `manual` keeps the current optional expense or income direction behavior.
- `reserve-payment` requires one valid commitment UUID and one valid selected
  period. Its direction is always expense.

Use an explicit query mode instead of accepting an arbitrary return URL. Reject
array values, incomplete payment parameter groups, an income direction paired
with a payment, malformed UUIDs, and malformed periods before any ledger read.
Existing `/transactions/new`, expense, and income links must keep their exact
behavior.

Extend `src/ui/transactions/transaction-create-contract.ts` with the smallest
read needed to resolve a payment target. Prefer the new period overview so the
route can verify the commitment is active, unpaid, next for its leaf, and backed
by an active reserve leaf. This load-time check supplies the form context and
early stale-link feedback; it is not the write authorization. Update the native
facade and test fakes. The web route keeps parsing only and never calls the read.

### Atomic payment mutation

Add a narrow reserve-payment data boundary, named for its outcome, such as
`src/data/reserve-payments.ts`. Its public create input contains the validated
commitment ID, selected period, and complete expense payload. Parse every value
before opening a transaction.

Use the existing `AtomicTransactionRunner` so the boundary performs these steps
inside one exclusive transaction:

1. Read the target commitment, active reserve category reference, and all
   payment candidates needed by the deterministic matcher for the selected
   period.
2. Reject a missing, deleted, inactive, already paid, non-next, or unavailable-
   leaf target.
3. Reject a payload whose direction or category does not match the payment
   intent, and apply the same account, date, category, period preparation, and
   current-income rules as UI-020.
4. Insert exactly one complete expense through a transaction-scoped helper
   shared with UI-020's manual create boundary.

Extract only the transaction-scoped complete-create logic needed by both public
boundaries after inspecting UI-020's final shape. Do not call one top-level
atomic boundary from inside another. The reserve-payment boundary owns the
transaction, then emits the same committed month-config and transaction
notifications after success. It emits nothing after a rejected or rolled-back
attempt. It stores no commitment ID on the transaction, so the category and
period matcher remains the authority for the resulting paid state.

Expose this as one `createReservePayment` call on the native transaction-create
facade. Keep manual creation on `createCompleteTransaction`. Add real SQLite
tests proving that a target changed after route loading is rejected and that a
competing commitment or payment mutation cannot interleave between eligibility
validation and insertion.

### Shared creator intent

Replace independent optional preset props with a discriminated
`TransactionCreationIntent` accepted by the pure initializer and
`TransactionCreator`:

- Manual creation carries its editable initial direction.
- Reserve payment carries the target commitment, reserve leaf reference, and
  selected period.

For reserve payment initialization:

- Set direction to expense and keep it fixed.
- Set the reserve leaf and keep it fixed.
- Leave amount blank. Show the reserved amount as context, not as transaction
  input.
- Default account to the one active default bank account.
- Default date to today's local date, never the resolved due date.
- Leave quality and note blank.
- Set payer to you, photo to null, source label to null, and adjustment effect
  to null through the existing complete-create payload builder.

Reuse `TransactionFormFields.tsx`. Add a discriminated presentation mode so the
payment form renders fixed expense and leaf context without offering controls
that would stop the result from matching. Keep amount, account, quality, date,
and note controlled and editable.

Add payment-context validation after the shared manual form validation. The
occurred date must belong to the selected period. Keep UI-020's write-boundary
future-date validation unchanged, so a forged or stale UI still cannot save a
future manual transaction. The atomic reserve-payment boundary repeats all
security and consistency checks; the form validation exists for immediate field
feedback. Do not write a commitment ID into the transaction note.

Preserve the existing synchronous submit lock, disabled navigation while the
write is unresolved, retained values after failure, and saved state after
commit. Manual intent makes exactly one `createCompleteTransaction` call.
Reserve-payment intent makes exactly one `createReservePayment` call. Neither
path performs a separate authorize-then-write sequence.

Extend `tests/transaction-form.logic.test.ts` and
`tests/transaction-create.component.test.tsx` for:

- Manual creation regression coverage.
- Blank payment amount with visible reserved amount context.
- Fixed expense direction and fixed reserve leaf.
- Default bank and today date.
- An actual amount that differs from the reserve amount.
- Current-period and explicit past-period dates.
- Same-period enforcement and future-date feedback.
- Null source, photo, and adjustment effect with payer set to you.
- Failed write retention and immediate duplicate event protection.
- A stale paid, inactive, non-next, missing, or unavailable-leaf target at load
  time stopping before form initialization.
- Any of those target changes after initialization being rejected by the atomic
  mutation without inserting an expense.

### Navigation after commit

Update `src/app/transactions/new.tsx` by intent:

- Manual creation keeps revealing the saved transaction and replacing with
  `/transactions`.
- Reserve payment does not change transaction-list filters. It replaces with
  `/settings/commitments?period=<selected-period>` after commit.
- Cancel goes back when history exists. A cold reserve-payment link replaces

- A navigation failure keeps the saved state and offers Back to commitments.

Update `src/app/transactions/new.web.tsx` to name reserve payment when the

Extend `tests/transaction-route.logic.test.ts` and
`tests/router-navigation.component.test.tsx` for every accepted and rejected

### Reserve payment

   period.
2. Save one payment through the atomic reserve-payment boundary with an amount
